# 402 光影獵人 LightCatcher

自然光影捕捉管家：黃金時刻/藍調時刻倒數、火燒雲指數、雲海指數＋雲海高度估算、觀星指數。山脈家族（k2, `#A64B38`）第三支，PWA 架構仿 400 走稜步道（單檔 hash 路由）。

原始需求：React Native+Expo+Supabase PRD，討論後改走純PWA。**2026-08-24 產品方向大幅簡化**（老闆實測後回饋）：拿掉Email登入/訂閱熱點/推播通知/打卡回報整套機制，全站改成完全開放瀏覽不用帳號；改成「首頁景點快選＋分開呈現各指數＋因子拆解＋雲海高度估算＋預測方法說明頁」，強調專業感與簡單操作。現在有4個畫面：首頁/地圖探索/預測說明/自訂選項。

## 現況：v0.7

**已上線 https://lightcatcher.pages.dev/**，4個畫面：首頁／地圖探索／預測說明／自訂選項。

### 目前有的功能
- 黃金/藍調時刻倒數（`suncalc`本機計算）
- 首頁景點快選：從Supabase `spots`表載入53個知名景點的快選按鈕，點了自動定位+抓氣象
- 機率預測**分開呈現**：選了特定景點只顯示該景點對應現象的指數卡（火燒雲/雲海/觀星擇一）；沒選景點(手動座標/GPS)則三張都顯示。每張卡都拆解出實際因子數值+子分數，不是單一黑箱數字
- **雲海高度估算**：用氣象學經典的LCL公式（`125×(氣溫-露點)`估算凝結高度），換算成海拔後跟景點高程比較，判斷機位在雲層之上/之中/之下
- 未來三日預測（會依選中景點類型只顯示相關指數）
- 地圖探索：Leaflet+OSM圖磚，**完全開放瀏覽不用帳號**，53個景點依機率變色，雲海類型景點popup會顯示雲海高度
- 「預測說明」頁：每個指數的計算邏輯、權重、資料來源，白紙黑字寫清楚建立可信度
- 稜線品牌footer + PWA安裝按鈕 + 正式icon(`sunset-2`)

### 首頁「今日推薦」（2026-08-24，老闆提議）
首頁最上方新增卡片，掃描全部53個景點今天/明早/今晚最近一次現象的分數，挑出「大景預警」(score>75，跟指數卡既有的門檻共用)的地點列出前3名，點了直接跳去看該景點的完整預測。**沒有後端排程**：靠瀏覽器localStorage存日期字串，同一支瀏覽器一天只掃一次(53個景點平行呼叫Open-Meteo，跟地圖探索頁邏輯相同)，換瀏覽器/清快取/隔天才會重算，不是全站共用同一份結果。每個景點只看它資料庫裡標記的現象類型(不會拿海邊景點去湊雲海分數)，目標時刻用suncalc算：火燒雲抓傍晚黃金時刻、雲海抓清晨黎明、觀星抓天文昏影結束(真正入夜)，時間已過1小時內算今天、超過就换算明天。今天全台都沒有大景預警就老實說「沒有特別突出」，不硬湊推薦。

**加回藍調時刻評分**（同日，老闆確認Phase 1的倒數計時器藍調時刻沒有配一個機率分數）：`weatherMath.js`新增`blueHourScore()`（雲量50%+能見度30%+濕度20%，門檻比觀星寬鬆因為藍調時刻本來就短暫些微雲層還能接受）。藍調時刻**不靠景點資料庫標記**（任何地點都適用，不像雲海/觀星需要地形/光害條件），所以：①「今日推薦」掃描時每個景點都會多算一組藍調時刻分數一起參與排名 ②首頁倒數計時卡片下面新增即時分數行(抓完氣象後顯示)，跟「今日推薦」共用同一套目標時刻計算(`nextPhenomenonTime`)，兩處數字對得起來。

### 新增第5種現象：琉璃光指數（同日，老闆提議）
南投金龍山最著名的夜間現象——逆溫困住谷地(魚池/埔里盆地)的霧，把下方城鎮燈光暈染成七彩光暈，跟雲海是同一套「逆溫困住谷地水氣」機制，差別是雲海白天看反光、琉璃光夜間看谷地燈光透霧。`weatherMath.js`新增`liuliGuangScore()`：逆溫強度(50%)+能見度(35%，跟雲海不同——這裡要「剛剛好」500~3000m最佳，太清澈看不出暈染感、太濃燈光整個被擋住，用三角形評分不是越低越好)+地表風速(15%)，**逆溫跟能見度用乘法不是加權平均**(其中一項是0代表沒有霧可言，整體該掉到接近0，不該被另一項平均掉)。

**這個指數只在資料庫明確標記過的地點顯示**，不像雲海/觀星可以套用在任何地點當附加參考——因為公式算不出「這個谷地下方到底有沒有城鎮燈光」這個地形前提，硬套會給出沒有意義的假分數。加入首頁精選景點快選(僅金龍山)、加入「今日推薦」排名(靠DB標記加入`TYPE_TO_KIND`，跟sea/glow/stars同一套邏輯)、目標時刻比照觀星抓真正入夜時段(同樣需要黑暗才看得到燈光透霧的效果)。

**補查5個地點共6筆liuli_guang標記**（同日，老闆問「還有哪些地點會有琉璃光」後主動查證）：`隙頂二延平`/`頂石棹`/`鹿谷大崙山銀杏森林`(本來就在53個景點裡，只是額外補標記，座標/海拔沿用老闆原本資料)、`埔里虎頭山`(23.9739,120.9821, 555m)/`梅山太平雲梯`(23.559601,120.60008, 1000m)(全新景點)——都有新聞/官方頁面直接點名「琉璃光」，座標查自公開網路資料(非老闆提供)。全部6個地點都刻意沒標記`stars`：城鎮燈光是必要條件同時也是光害，兩者互斥。搜尋過程還看到「武界開心茶園」「二尖山」零星提及但證據不夠具體，先不加。**已跑進正式Supabase**（2026-08-24執行`seed.sql`，53→56個景點，74筆，已用REST API查證6筆liuli_guang都在且標記正確）。

### 未來三日預測可展開查看詳細因子拆解（同日，老闆要求）
點開每天可以看到跟「現在」預測一樣的完整卡片(含因子拆解)，不再只有一個分數badge。**順便修正一個潛藏問題**：原本三日預測全部套用同一個「傍晚黃金時刻」時間點算分，雲海該用清晨、觀星/琉璃光該用夜間，卻都被塞進傍晚那個時間點算——因為原本只顯示badge數字看不出時段不對，這次要攤開因子細節才發現。已修正成每個現象各自抓合理時段。

### GPS定位錯誤訊息改善（同日，老闆回報「使用目前位置」疑似失敗）
`getCurrentPosition`原本沒設timeout，遇到裝置沒回應時會無限卡在「定位中…」；也沒用`error.code`分辨失敗原因，一律顯示「定位失敗」。改成10秒逾時＋依code給明確訊息(權限被拒/裝置無法定位/逾時)。用Puppeteer模擬CDP授權/拒絕定位權限兩種情境驗證過都正常運作——但**headless測試模擬不到真實裝置的定位權限彈窗行為**，如果老闆是直接雙擊打開本機`index.html`(file://)測試，Chrome對file://來源的定位API預設會直接擋掉(不會跳權限詢問)，這種情況要改用`https://lightcatcher.pages.dev/`正式站測試才準。

### 記住上次選的地點（同日，老闆要求「不用選」）
`setCoords()`每次呼叫都把`{lat,lng,source,selectedSpot}`存進localStorage(`lc_last_location_v1`)，開啟App時`restoreLastLocation()`自動讀回並直接觸發抓取氣象，不用重新選一次。因為GPS/手動輸入/景點快選/地圖popup/今日推薦點進來全部都經過同一個`setCoords()`，這個記憶邏輯自然涵蓋所有選地點的路徑。**是per-browser的localStorage，不是登入後跨裝置同步**——換瀏覽器/清快取會回到「尚未定位」。

### 新增「自訂選項」頁籤（同日，老闆要求）
第4個nav分頁，3張卡片：①**自訂常用地點**——自己輸入座標+命名存進localStorage(`lc_custom_spots_v1`)，可新增/使用/刪除，使用時視同手動座標(不套DB景點的雲海/觀星等標記) ②**上次記住的地點**——顯示目前記住的內容+一鍵清除重設 ③**深色模式**——只調整結構性中性色(頁面底色/文字/邊框/卡片底色)，`.rl-appbar`跟`.update-bar`這兩個「常駐深色列」刻意用獨立的`--bar-bg`/`--bar-fg`固定色，不隨主題變化(避免頭尾被反白搞壞品牌識別)。`<head>`加了提早讀localStorage設`data-theme`的inline script，避免翻頁閃一下淺色。

## 評分公式現況（重要：目前是「方向正確、可運作」的推估係數，不是精雕過的權重）

PRD 只給了每個因子的方向（越低越好/40-70%最佳等），沒給精確的分段函數參數。`weatherMath.js` 裡的門檻值（例如低雲30%開始扣分、濕度75%分界）是照PRD方向自訂的線性/三角形插值，**之後要依老闆實際使用回饋校準**，不要當成已驗證過的氣象學公式。
